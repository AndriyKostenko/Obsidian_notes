### Короткий ответ
**Нет, `POST`-запрос по умолчанию не является идемпотентным.** Каждый вызов обычно приводит к созданию нового ресурса, поэтому повторный запрос меняет состояние сервера. Однако идемпотентность можно добавить вручную на уровне реализации.

---

## 🔍 Что такое идемпотентность?

Идемпотентность (от греч. *idem* "тот же" + *potentia* "сила") – свойство операции, при котором **многократное выполнение даёт тот же результат, что и однократное**.

📐 Математически: `f(f(x)) = f(x)`  
🌐 В контексте HTTP: сколько раз вы ни отправите запрос, **состояние сервера после первого успешного выполнения больше не меняется**.

⚠️ Важно не путать с **безопасностью (safe methods)**:
- `GET`, `HEAD`, `OPTIONS` – безопасные (не меняют состояние) и идемпотентные
- `PUT`, `DELETE` – **не безопасные**, но **идемпотентные**
- `POST`, `PATCH` – **не безопасные и не идемпотентные** по спецификации HTTP

---

## 🧪 Пример на FastAPI: почему `POST` не идемпотентен

```python
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()
db = []

class Item(BaseModel):
    name: str

@app.post("/items/")
def create_item(item: Item):
    db.append(item)
    return {"status": "created", "total": len(db)}
```

📡 Что произойдёт при повторных вызовах:
```bash
curl -X POST http://localhost:8000/items/ -d '{"name":"Apple"}'
# → {"status": "created", "total": 1}

curl -X POST http://localhost:8000/items/ -d '{"name":"Apple"}'
# → {"status": "created", "total": 2}  ← состояние изменилось!
```
Запрос **не идемпотентен**: два вызова создали два ресурса.

---

## 🛠 Как сделать `POST` идемпотентным?

Идемпотентность зависит от **реализации**, а не только от HTTP-метода. Самый распространённый паттерн – **Idempotency Key**:

```python
from fastapi import FastAPI, Header, HTTPException
from pydantic import BaseModel
import uuid

app = FastAPI()
db = []
processed_keys = set()  # В проде: Redis/DB с TTL

class Item(BaseModel):
    name: str

@app.post("/items/")
def create_item(
    item: Item,
    idempotency_key: str = Header(..., alias="Idempotency-Key")
):
    if idempotency_key in processed_keys:
        return {"status": "already_processed", "idempotency_key": idempotency_key}
    
    processed_keys.add(idempotency_key)
    db.append(item)
    return {"status": "created", "id": str(uuid.uuid4())}
```

Теперь при повторном запросе с тем же заголовком:
```bash
curl -X POST http://localhost:8000/items/ \
  -H "Idempotency-Key: req_123" \
  -d '{"name":"Apple"}'
# → {"status": "already_processed", ...}
```
Запрос стал **идемпотентным**.

> 💡 В реальных системах (`Stripe`, `AWS`, платёжные шлюзы) ключ идемпотентности хранят в Redis/БД с TTL 24–48 часов, а возвращают **тот же ответ**, что и при первом успешном вызове.

---

## ✅ Альтернатива: использовать `PUT` для идемпотентного создания

Если вам нужно гарантировать идемпотентность "из коробки", лучше сменить семантику:

```python
@app.put("/items/{item_id}")
def upsert_item(item_id: str, item: Item):
    # Заменяет или создаёт ресурс с известным ID
    return {"id": item_id, "name": item.name, "action": "upserted"}
```
`PUT` идемпотентен по спецификации: повторные запросы с теми же данными не меняют состояние после первого применения.

---

## 📌 Ключевые выводы

| Метод | Идемпотентен? | Почему |
|-------|---------------|--------|
| `GET`, `HEAD`, `OPTIONS` | ✅ Да | Не меняют состояние |
| `PUT`, `DELETE` | ✅ Да | Повторное применение = тот же результат |
| `POST` | ❌ Нет (по умолчанию) | Создает новый ресурс при каждом вызове |
| `PATCH` | ❌ Нет (по умолчанию) | Частичное обновление может накапливаться |

- Идемпотентность **реализуется в коде**, а не диктуется жестко методом.
- В микросервисах и платёжных системах идемпотентность `POST` критична для **безопасных повторных запросов (retries)** при сетевых ошибках.
- Если вам нужна гарантированная идемпотентность – используйте `PUT` с уникальным ID или заголовок `Idempotency-Key`.
