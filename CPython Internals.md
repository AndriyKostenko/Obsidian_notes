
Давай разберем архитектуру CPython по шагам: от твоего исходного кода до процессора.

---

### 1. Общая архитектура: Компилятор + Виртуальная Машина

Вопреки популярному мифу, Python — это не чистый интерпретатор. Это **компилятор + виртуальная машина**.

Процесс запуска скрипта выглядит так:
1.  **Токенизация:** Исходный текст разбивается на лексемы (ключевые слова, имена, числа).
2.  **Парсинг:** Лексемы превращаются в **АСТ (Абстрактное Синтаксическое Дерево)**.
3.  **Компиляция:** АСТ превращается в **Байт-код** (набор инструкций для виртуальной машины).
4.  **Выполнение:** Виртуальная машина (VM) исполняет байт-код.

---

### 2. Что происходит, когда ты пишешь `x = 10`?

Давай пройдем этот путь детально.

#### Шаг 1: Компиляция в байт-код
Когда ты запускаешь файл, CPython сначала компилирует его в байт-код (который обычно кэшируется в папке `__pycache__` с расширением `.pyc`).

Ты можешь увидеть этот байт-код с помощью модуля `dis` (disassembler):

```python
import dis

def foo():
    x = 10
    return x

dis.dis(foo)
```

Вывод будет примерно таким:
```text
  2           0 LOAD_CONST               1 (10)
              2 STORE_NAME               0 (x)
  3           4 LOAD_NAME                0 (x)
              6 RETURN_VALUE
```

*   `LOAD_CONST 1 (10)`: Положить константу `10` на вершину стека.
*   `STORE_NAME 0 (x)`: Снять значение со стека и сохранить его в словарь локальных переменных под именем `x`.

#### Шаг 2: Создание объекта в памяти
В Python **всё есть объект**. Число `10` — это не просто биты в памяти, это структура в куче (heap).

В исходном коде CPython (файл `include/cpython/object.h`) базовый объект выглядит упрощенно так:

```c
typedef struct _object {
    Py_ssize_t ob_refcnt;      // Счетчик ссылок
    struct _typeobject *ob_type; // Указатель на тип (например, int)
} PyObject;
```

Когда выполняется `LOAD_CONST 1 (10)`:
1.  CPython проверяет, есть ли уже объект "целое число 10" в памяти.
2.  **Оптимизация:** Маленькие целые числа (обычно от -5 до 256) **кешируются** при старте интерпретатора. Поэтому новый объект не создается, используется существующий.
3.  Если бы это было `x = 1000`, был бы выделен новый блок памяти под `PyObject`, в `ob_type` записался бы тип `int`, а `ob_refcnt` стал бы равен 1.

#### Шаг 3: Работа с именами (Переменные)
Важно понять: **в Python нет переменных в смысле C++**. Есть **имена** (labels), которые ссылаются на объекты.

Когда выполняется `STORE_NAME 0 (x)`:
1.  Виртуальная машина берет текущий **фрейм** (контекст выполнения функции).
2.  У фрейма есть словарь локальных имен (`f_locals`).
3.  В этот словарь записывается пара ключ-значение: `{"x": <ссылка на объект 10>}`.

То есть `x` — это просто строка-ключ в хэш-таблице, которая указывает на адрес объекта `10` в памяти.

---

### 3. Виртуальная Машина (The Eval Loop)

Сердце CPython находится в файле `Python/ceval.c`. Там находится главный цикл интерпретатора (`_PyEval_EvalFrameDefault`).

Это огромный цикл `switch`, который перебирает байт-код инструкции за инструкцией.

**Как работает стек:**
VM Python — **стековая**. У неё нет регистров для хранения промежуточных данных (как в процессоре).
*   Чтобы сложить `a + b`, VM делает:
    1.  `LOAD_NAME a` (push в стек)
    2.  `LOAD_NAME b` (push в стек)
    3.  `BINARY_ADD` (pop два значения, сложить, push результат)

**Фреймы (Frames):**
Каждый вызов функции создает новый объект `PyFrameObject`. В нем хранятся:
*   Локальные переменные.
*   Стек для вычислений.
*   Указатель на текущую инструкцию (Instruction Pointer).
*   Ссылка на предыдущий фрейм (для возврата из функции).

---

### 4. Управление памятью

Это одна из самых важных частей.

#### 1. Счетчик ссылок (Reference Counting)
У каждого объекта есть поле `ob_refcnt`.
*   Когда ты делаешь `y = x`, счетчик объекта, на который ссылается `x`, увеличивается на 1.
*   Когда область видимости заканчивается или переменная переназначается, счетчик уменьшается.
*   **Когда счетчик становится 0**, память освобождается **мгновенно**.

Это объясняет, почему в Python нет явной очистки памяти, но также почему циклические ссылки опасны (объект А ссылается на Б, Б на А -> счетчики никогда не станут 0).

#### 2. Сборщик мусора (Garbage Collector)
Для борьбы с циклическими ссылками есть отдельный циклический GC (модуль `gc`). Он периодически запускается, ищет группы объектов, которые ссылаются друг на друга, но не достижимы извне, и удаляет их.

#### 3. Менеджер памяти (pymalloc)
Python не обращается к `malloc` ОС для каждого маленького объекта (это медленно). У него свой аллокатор (`Objects/obmalloc.c`). Он выделяет большие куски памяти у ОС, а внутри делит их на блоки фиксированного размера (пулы) для мелких объектов.

---

### 5. GIL (Global Interpreter Lock)

Нельзя рассказывать о CPython и не упомянуть GIL.

Внутри `ceval.c` есть механизм блокировки. **Только один поток может исполнять байт-код Python в один момент времени.**

*   **Зачем:** Чтобы упростить управление памятью (счетчик ссылок не требует атомарных операций в каждом потоке, так как поток захватил лок).
*   **Последствие:** Многопоточность в Python не ускоряет вычисления на многоядерных CPU (для CPU-bound задач). Она полезна только для I/O (ожидание сети/диска), так как во время ожидания GIL отпускается.

---

### 6. Итого: Полный путь выполнения

Допустим, ты написал скрипт `test.py`:

```python
a = 5
b = 10
c = a + b
print(c)
```

1.  **Запуск:** Ты пишешь `python test.py`.
2.  **Чтение:** ОС загружает исполняемый файл `python`, который запускает `main()` в `Modules/main.c`.
3.  **Компиляция:**
    *   Текст читается, разбивается на токены.
    *   Строится АСТ.
    *   Генерируется байт-код (инструкции `LOAD_CONST`, `STORE_NAME`, `BINARY_ADD`, `CALL_FUNCTION`).
4.  **Инициализация:** Создается интерпретатор, инициализируются типы (int, str, list...), создаются кэши маленьких чисел.
5.  **Выполнение (Eval Loop):**
    *   Создается главный фрейм (`__main__`).
    *   `LOAD_CONST 5` -> Объект 5 (из кэша) кладется в стек.
    *   `STORE_NAME 'a'` -> В словарь `globals` пишется `'a': <obj 5>`.
    *   ... (аналогично для `b`).
    *   `LOAD_NAME 'a'`, `LOAD_NAME 'b'` -> Два объекта в стек.
    *   `BINARY_ADD` -> Вызывается C-функция `PyNumber_Add`. Она создает **новый** объект `15` (так как 15 тоже в кэше, вернется ссылка на кэш).
    *   `STORE_NAME 'c'`.
    *   `CALL_FUNCTION print` -> Создается новый фрейм для функции `print`, выполняется её байт-код.
6.  **Завершение:** Счетчики ссылок на локальные объекты падают, память освобождается, процесс завершается.

### Как посмотреть самому?

Если хочешь покопаться глубже:
1.  **Байт-код:** `import dis; dis.dis(твоя_функция)`
2.  **Ссылки:** `import sys; sys.getrefcount(объект)` (осторожно, сам вызов функции временно увеличивает счетчик).
3.  **Исходный код:** Репозиторий [github.com/python/cpython](https://github.com/python/cpython).
    *   `Python/ceval.c` — логика выполнения.
    *   `Objects/` — реализация типов (int, list, dict).
    *   `Include/` — заголовочные файлы (структуры данных).

Понимание этой механики помогает осознать, почему, например, изменение глобальной переменную внутри функции требует `global`, почему кортежи быстрее списков (они проще устроены внутри) и почему `is` сравнивает адреса объектов, а `==` вызывает метод `__eq__`.



Именно поэтому в Python часто советуют не использовать изменяемые типы (списки, словари) в качестве значений аргументов по умолчанию (`def func(x=[])`), потому что один и тот же объект-список будет использоваться во всех вызовах функции.

### ASSISTANT
Это отличный вопрос, который касается самого фундамента CPython. Чтобы понять, где что хранится, нужно сразу отбросить модель памяти из языков вроде C или C++, где есть четкое разделение: «переменные на стеке, объекты в куче».

В Python модель проще и одновременно сложнее: **всё является объектом, и почти всё хранится в куче (Heap).**

Давай разберем по полочкам: переменные, функции, классы и то, как этим управляет память.

---

### 1. Главное правило: Всё в Куче (Heap)

В CPython **нет понятия «переменная хранит значение»**.
*   **Значения (объекты):** Числа, строки, списки, функции, классы, модули — **всё это объекты**, выделенные в динамической памяти (в куче).
*   **Имена (переменные):** Это просто записи в словарях (хэш-таблицах), которые называются **Пространствами имен (Namespaces)**.

#### Где хранятся объекты?
В специальной области памяти, управляемой интерпретатором. Каждый объект имеет заголовок (счетчик ссылок, тип) и тело (данные).

#### Где хранятся имена (переменные)?
Они хранятся в **словарях (dict)**:
1.  **Глобальные переменные:** В словаре модуля (`module.__dict__`).
2.  **Локальные переменные функции:** В объекте фрейма (`frame.f_locals` или оптимизированный массив).
3.  **Атрибуты объекта:** В словаре экземпляра (`instance.__dict__`).

---

### 2. Детальный разбор: Что где лежит?

Представим такой код:

```python
x = 10                  # 1. Переменная

def my_func():          # 2. Функция
    return x

class MyClass:          # 3. Класс
    val = 5

obj = MyClass()         # 4. Экземпляр
```

#### 1. Переменная `x = 10`
*   **Объект `10`:** Лежит в **Куче**. Это объект типа `int`.
    *   *Нюанс:* Числа от -5 до 256 создаются один раз при старте интерпретатора (кэш). `x` просто ссылается на этот общий объект.
*   **Имя `x`:** Лежит в **словаре глобальной области видимости** (глобальный `dict` модуля).
    *   Запись: `{'x': <ссылка на объект 10>}`.

#### 2. Функция `my_func`
Функция в Python — это полноценный объект!
*   **Объект функции:** Лежит в **Куче**. Тип: `function`.
    *   Внутри него хранятся:
        *   Ссылка на **Code Object** (скомпилированный байт-код).
        *   Ссылка на глобальный словарь (`__globals__`).
        *   Имя функции, аргументы по умолчанию и т.д.
*   **Code Object:** Тоже объект в **Куче**. Содержит сам байт-код, таблицу констант, имена переменных. Он неизменяемый.
*   **Имя `my_func`:** Лежит в **глобальном словаре** модуля.

#### 3. Класс `MyClass`
Класс — тоже объект (экземпляр метакласса `type`).
*   **Объект класса:** Лежит в **Куче**.
    *   Внутри хранит атрибуты класса (например, `val`), методы, ссылку на базовые классы.
*   **Атрибут `val`:** Хранится в словаре класса (`MyClass.__dict__`).
*   **Имя `MyClass`:** Лежит в **глобальном словаре** модуля.

#### 4. Экземпляр `obj`
*   **Объект `obj`:** Лежит в **Куче**.
    *   У него есть заголовок (ссылка на класс `MyClass`, счетчик ссылок).
    *   У него есть словарь экземпляра (`obj.__dict__`), где хранятся атрибуты объекта (если ты сделаешь `obj.a = 1`, это попадет сюда).
*   **Имя `obj`:** Лежит в **глобальном словаре** модуля.

### 3. Как устроена память внутри (CPython Memory Manager)

CPython не просит у операционной системы память (`malloc`) для каждого маленького объекта. Это было бы очень медленно. Вместо этого используется многоуровневая система.

#### Уровень 1: Raw Memory (ОС)
Python запрашивает у ОС большие куски памяти (арены), обычно по 256 КБ.

#### Уровень 2: pymalloc (Менеджер памяти Python)
Внутри этих арен Python организует свою структуру (**Objects/obmalloc.c**):
1.  **Arena (Арена):** Большой блок памяти от ОС.
2.  **Pool (Пул):** Арена делится на пулы. Каждый пул обслуживает объекты определенного размера (например, только объекты по 32 байта, или только по 64 байта).
3.  **Block (Блок):** Пул делится на блоки. Это место, где живет твой объект.

**Зачем это нужно?**
*   **Скорость:** Выделение памяти из пула быстрее, чем вызов `malloc` в ОС.
*   **Отсутствие фрагментации:** Маленькие объекты не разбрасываются по всей памяти, а лежат компактно в пулах.
*   **Возврат памяти:** Когда пул становится полностью пустым, он возвращается в арену, а когда арена пустеет — память возвращается ОС.

#### Уровень 3: Объекты
Непосредственно твои данные (`int`, `list`, `dict`). Они занимают блоки в пулах.

---

### 4. Управление жизненным циклом (Удаление)

Как Python понимает, что объект можно удалить?

#### 1. Счетчик ссылок (Reference Counting) — Основной механизм
У каждого объекта в заголовке есть поле `ob_refcnt`.
*   Создал объект: `refcnt = 1`.
*   Присвоил переменной: `refcnt += 1`.
*   Удалил переменную (`del x` или выход из области видимости): `refcnt -= 1`.
*   **Если `refcnt == 0`:** Память освобождается **мгновенно**. Блок возвращается в пул.

#### 2. Сборщик мусора (Garbage Collector) — Для циклов
Счетчик ссылок не справляется с циклическими ссылками:
```python
a = []
b = []
a.append(b)  # a ссылается на b
b.append(a)  # b ссылается на a
del a
del b        # Счетчики стали 0? Нет, они ссылаются друг на друга!
```
Для этого есть **GC** (модуль `gc`). Он периодически запускается и ищет такие «острова» объектов, которые ссылаются друг на друга, но на которые нет ссылок извне (из кода программы). Он разрывает циклы и очищает память.

### 5. Визуализация памяти для простого скрипта

Допустим:
```python
a = 100
b = a
```

**В памяти (Heap):**
1.  **Объект Int(100):**
    *   Адрес: `0x1000`
    *   Тип: `int`
    *   Значение: `100`
    *   `refcnt`: 2 (потому что на него ссылаются `a` и `b`)

**В памяти (Namespace Dict):**
1.  **Глобальный словарь модуля:**
    *   Ключ `"a"` -> Значение `0x1000` (указатель)
    *   Ключ `"b"` -> Значение `0x1000` (указатель)

**Что происходит при `a = 200`?**
1.  Создается (или берется из кэша) объект `Int(200)` по адресу `0x2000`.
2.  В словаре модуля ключ `"a"` обновляется на `0x2000`.
3.  Счетчик ссылок объекта `Int(100)` уменьшается на 1 (становится 1, так как `b` еще ссылается).
4.  Счетчик ссылок объекта `Int(200)` увеличивается.

---

### 6. Оптимизация памяти (Что стоит знать)

1.  **Interning (Интернирование):**
    *   Короткие строки и маленькие целые числа кэшируются. `a = "hello"`, `b = "hello"` -> `a is b` будет `True`. Это экономит память.
2.  **`__slots__`:**
    *   По умолчанию у каждого экземпляра класса есть свой словарь `__dict__` для атрибутов. Это занимает много памяти.
    *   Если объявить `__slots__ = ['x', 'y']`, Python выделит фиксированную память под эти атрибуты (как в struct в C), без словаря. Экономия до 40-50% памяти для миллионов объектов.
3.  **Локальные переменные функций:**
    *   Хотя логически это словарь, CPython оптимизирует доступ к локальным переменным внутри функции. Они хранятся в массиве (`fast locals`) внутри фрейма, а не в хэш-таблице, что делает доступ к ним быстрее, чем к глобальным.

### Итог

1.  **Объекты (данные):** Живут в **Куче (Heap)**, управляемой `pymalloc`.
2.  **Переменные (имена):** Живут в **Словарях (Namespaces)**, которые тоже лежат в куче.
3.  **Функции и Классы:** Это такие же объекты в куче, просто более сложные по структуре.
4.  **Стек:** Используется только для вызовов C-функций внутри самого интерпретатора и для хранения фреймов вызовов (но сами фреймы выделяются в куче).
5.  **Очистка:** Мгновенная через счетчик ссылок + периодическая для циклов через GC.

Эта модель («всё объект, всё в куче, имена — ссылки») делает Python гибким, но накладывает накладные расходы на память и скорость по сравнению с компилируемыми языками.
